# Events–State–Observations Architecture Assessment

> **Date:** 2026-08-20
> **Scope:** Formalize the Events–State–Observations philosophy as a first-class architectural principle, assess the current Java implementation against it, and produce a staged backlog. This document does not implement the refactor.

## Canonical invariant

```text
Events mutate State.
State produces Observations.
Observations inform Decisions.
Decisions produce Events.
```

See `docs/architecture.md` (section "Core Architecture Philosophy: Events, State, Observations") for the full narrative treatment of Events, State, Observations, and Decisions, and for the list of signals that should trigger architectural review.

## Update 2026-08-20 — Pricing/order semantics resolved

A follow-up product clarification resolves the "domain decision required" flagged below for revenue timing, and **overrides that section's conclusion**. It also refines the code fix already merged for the `SnapshotBuilder` bug (see below). This update does not replace the rest of the assessment — the architecture matrix (B) and backlog (C) are amended in place; everything not touched here still stands.

**Resolution.** `price` was never one concept. Arcogine distinguishes:

| Concept | Meaning | Owner / location | Mutability |
|---|---|---|---|
| **OfferPrice** | The simulated firm's current asking price; input to the demand model. (Terminology corrected 2026-08-20 (3) — see below; was called "MarketPrice" in this section originally, which overloaded the term with a future external-market concept.) | `PricingState` | Mutable, changes on `PriceChange` |
| **OrderPrice** (unit price) | Price agreed when a specific order was created. | Captured on `OrderCreation`, carried by the order/job | Immutable once the order exists |
| **OrderValue** | `quantity x OrderPrice` for one order. | Derived from the order | Derived |
| **CompletedSalesValue** | Sum of `OrderValue` for completed orders. | Factory/operational KPI | Accumulates using each order's own `OrderPrice` |
| Revenue | Reserved for a future finance/accounting domain (recognition policy, receivables, deferred revenue, etc.) | Not modeled | — |

The previously open question — "does revenue use price-at-order-creation or price-at-completion?" — is **resolved as price-at-order-creation**: `OrderPrice` is captured once, at `OrderCreation`, and is immutable for the life of the order. `OfferPrice` changes only affect orders created *after* the change. This is a product decision about commercial transaction semantics, not the introduction of an accounting model — see `docs/architecture.md`'s "Pricing, orders, and money" section and `docs/concepts.md`'s "Completed sales value" section for the full narrative and the explicit non-goal (no `RevenueRecognitionPolicy`, `AccountsReceivable`, `PaymentTerms`, `CashReceipt`, `AccruedRevenue`, or `DeferredRevenue`).

**This changes the classification of code inspected in the original review:**

- `PricingState.currentPrice` → this **is** `OfferPrice`. Correctly named conceptually (if not literally), correctly the sole event-driven owner. No change to its role.
- `DemandModel.currentPrice` → also `OfferPrice` (a copy). `DemandModel` correctly uses it only to compute demand and only for orders not yet created — using `OfferPrice` here is correct by construction; the problem was always the duplicate mutable copy, not the semantic.
- `EventPayload.OrderCreation(ProductId productId, long quantity)` → **gap**. It captures `quantity` but not `OrderPrice`, even though the product decision requires the order's unit price to be fixed at exactly this event. This is the central structural gap the new backlog item below closes.
- `FactoryHandler.currentPrice` (set via `setCurrentPrice`, pushed from `PricingState` by `IntegratedHandler` every event) → **misclassified concept**, not just duplicated state. The factory has no legitimate reason to know `OfferPrice` at all under the resolved semantics — it should only ever need each order's own `OrderPrice`, captured once at creation. This is stronger than the original finding ("duplicated state, sync it or read on demand") — the correct fix is to **delete** `FactoryHandler.currentPrice`/`setCurrentPrice` entirely, not to have `FactoryHandler` read `PricingState` on demand.
- `FactoryHandler.totalRevenue` / `handleTaskEnd`'s `totalRevenue += currentPrice * job.quantity()` → this **is** `CompletedSalesValue` conceptually, but computed from the wrong input (`OfferPrice`/`currentPrice` at completion time) instead of the right one (each order's own `OrderPrice`, captured at creation). Needs both a rename (to `completedSalesValue`) and a computation fix (source the price from the order, not from live pricing state).
- `Job` → currently has no field for its own agreed price. This needs to change (see amended backlog item below) — this is where `OrderPrice`/`OrderValue` belong.
- `AgentObservation.currentPrice` / `AgentObservation.totalRevenue` → these **are** `OfferPrice` and `CompletedSalesValue` respectively; rename for precision, no semantic change — the agent already only ever reads `currentPrice` to decide a *new* `OfferPrice` (`SalesAgent.decide()`), never to touch any order's terms, so `SalesAgent`'s behavior already matches the resolved capability boundary ("agent observes/decides OfferPrice, never reprices existing orders"). This should be asserted by a test (see amended backlog), not just be true by absence of code that would violate it.
- `FactoryHandler.completedSales` → count of completed orders/jobs, distinct from `completedSalesValue` (monetary). Already distinct in the code (two separate fields); just confirm naming doesn't conflate them once `totalRevenue` is renamed.

**This changes the classification of the fix already merged for the `SnapshotBuilder` bug** (commit `e5ca23b`, "fix(revenue): fix per-job revenue in API snapshots to use completion price"). That fix correctly closed the *inconsistency* between `SnapshotBuilder`'s per-job number and `FactoryHandler.totalRevenue` (both now agree with each other) — but it fixed it by capturing `Job.revenue` at **task-end/completion time** (`FactoryHandler.currentPrice` as of `handleTaskEnd`), which is now known to be the wrong semantic per the resolved decision. It should have captured the price at **order-creation time** instead. The bug it fixed (aggregate vs. per-job disagreement) stays fixed either way; what changes is *which* price both numbers should agree on. This is now the first item in the amended backlog (P0, superseding the "SnapshotBuilder per-job revenue" backlog item below) — since it directly continues that just-shipped change, it is small, well-scoped, and covered by the same tests, it can reasonably be picked up next rather than deferred, but it is still a deliberate follow-up rather than something to silently fold into this document.

**Coupling implication (was Task 6 in the original review, `PricingState → FactoryHandler` sync).** Under the resolved semantics, the factory never needs `OfferPrice` — it only needs each order's own `OrderPrice`, which arrives already attached to `OrderCreation`. So `IntegratedHandler.factory.setCurrentPrice(pricing.currentPrice())` and `FactoryHandler.currentPrice`/`setCurrentPrice` should be deleted outright, not merely refactored into a read-on-demand interface. This is a stronger, simpler outcome than the original assessment's P1 item ("remove pushed copies, read on demand") for this specific edge — confirmed by the implementation, not merely suspected. The `DemandModel.currentPrice` duplication (still legitimately `OfferPrice`, still duplicated across `PricingState`/`DemandModel`) is unaffected by this update and still needs the P1 "read on demand" treatment from the original backlog.

See the amended matrix (B) and backlog (C) rows below for the concrete follow-up. Rows not mentioned there are unaffected by this update.

## Update 2026-08-20 (2) — Finance established as a domain, now

A second follow-up refines the previous position on revenue/accounting. The earlier statement —

> Revenue is reserved for a future finance/accounting domain and is not currently modeled.

— is replaced with:

> Arcogine establishes a minimal Finance domain now, with a deliberately minimal double-entry ledger, so financial interpretation has a clear owner before monetary concepts leak into Factory or Economy the way `currentPrice` once leaked into `FactoryHandler`. Accounting *sophistication* (recognition policy, receivables, tax, multi-currency) remains future scope — the domain boundary does not.

This is a scope decision, not an implementation in this pass — `sim-finance` does not exist yet. What changes here is the target architecture and backlog; see `docs/architecture.md`'s new "Commercial, Operational, and Financial Truth" section for the full narrative (three kinds of truth — commercial/operational/financial — related by events, never interchangeable; the initial immediate-settlement policy; why Finance now rather than later; the `OrderCompleted` event; the minimal double-entry mechanism; the money-representation boundary; the ownership table; agent/observation capability boundaries).

**Three kinds of truth, and who owns each** (full table in `docs/architecture.md`):

| Concept | Owner |
|---|---|
| `ObservedMarketPrice` (external market signal) | Future environment/market domain; not currently required |
| `OfferPrice`, demand state | Economy (`PricingState`, `DemandModel`) |
| `OrderPrice`, `OrderValue` | Immutable commercial order data (`Job`) |
| Production state, order completion (operational fact) | Factory (`FactoryHandler`) |
| Backlog / throughput / lead time | Factory, or a KPI/projection layer |
| Ledger, cash, sales financial balance, future receivables/payables | Finance (**new**, not yet implemented) |

**Reassessing `CompletedSalesValue` (Task 7 of the follow-up prompt).** The prior pass established `FactoryHandler.completedSalesValue` as the replacement for `totalRevenue`. That naming and computation are still correct as an **operational/commercial KPI** ("what commercial value has completed production?") — but it must not be confused with a future Finance-owned "Sales" balance ("what has been financially recorded under the active policy?"). Under the initial immediate-settlement policy these numbers will coincide, but they are not the same concept and are not guaranteed to stay equal once Finance's policy gains payment terms or other timing effects. `CompletedSalesValue` stays where it is (Factory, computed from completed orders' own `OrderValue`) — moving it into a KPI/projection layer is not required by this decision, since it's already a simple derived sum over authoritative operational facts (`Job.orderValue()`), not a second mutable accumulator; revisit only if a real second consumer of the same derivation appears.

**Event vocabulary gap.** `TaskEnd` currently means "a production step finished" — nothing today expresses "the order fulfilled its operational lifecycle" as a first-class fact. `FactoryHandler.handleTaskEnd` checks `job.isComplete()` internally but does not emit anything downstream-observable for that specific fact; `completedSalesValue`/`completedSales` are updated in-place, not announced. A Finance domain needs the latter, named fact, not an inference from the former. See the new `OrderCompleted` backlog item below.

**Non-goal refinement (Task 13).** Section D's "No accounting/finance model" bullet is refined in place below to "No sophisticated accounting model" — the minimal double-entry ledger is intentional current architecture, not a non-goal.

See the amended matrix (B) and backlog (C) rows below.

## Update 2026-08-20 (3) — Pricing vocabulary corrected: `OfferPrice`, not `MarketPrice`

A terminology-only amendment, not a scope change: everywhere the prior updates used **`MarketPrice`** for the firm's own mutable asking price, that term is corrected to **`OfferPrice`**. This document, `docs/architecture.md`, `docs/concepts.md`, and `CONTRIBUTING.md` have all been updated in place (the historical narrative above — "Update 2026-08-20" and "Update 2026-08-20 (2)" — keeps its prose as originally written except for this terminology swap; no conclusions changed).

The reason: "market price" implies an external/environmental signal (what the broader market says a product is worth), which Arcogine does not model. What Arcogine actually has is the firm's own controllable asking price. Conflating the two would misname a future concept before it exists. The corrected vocabulary:

| Concept | Meaning | Status |
|---|---|---|
| `ObservedMarketPrice` | External/environmental market signal | **Not implemented** — reserved for a future environment/market domain |
| `OfferPrice` | The firm's current asking price (was called `MarketPrice` above) | Implemented — `PricingState.currentPrice` |
| `OrderPrice` | Price agreed for an accepted order | Implemented — `Job.unitPrice` |
| `OrderValue` | `quantity x OrderPrice` | Implemented — `Job.orderValue()` |

The invariant: **the environment may inform `OfferPrice`; the firm controls `OfferPrice`; accepting an order freezes that price into `OrderPrice`; Finance later consumes the resulting immutable commercial facts.** `ObservedMarketPrice` does not need to be implemented now — there is no external market/environment model in Arcogine — and this amendment does not introduce settlement pricing, indexed contracts, rebates, or discounts. `OrderPrice = OfferPrice at OrderCreation` remains the entire rule.

Two source-level Java comments/test names used "MarketPrice" in prose (not as an identifier — no Java field, class, or method was ever named `MarketPrice`) and have been corrected to match: `EventPayload.OrderCreation`'s Javadoc, and a test method name in `SnapshotBuilderTest`/prose in `SnapshotBuilderTest`/`FactoryHandlerTest`. These are comment/name-only changes with no behavioral difference — not a violation of the "documentation and backlog only" scope for this series of updates.

## D. Explicit non-goals (for this pass and near-term follow-up)

- **No generic event bus / pub-sub.** Arcogine's value is explicit, deterministic, easy-to-read execution order. A bus would trade that for indirection the task explicitly asked to avoid.
- **No CQRS framework or event-sourcing framework.** The existing `Event`/`EventLog`/`Scheduler` triad already gives replayability where it's needed; adopting a framework would add ceremony without a demonstrated need.
- **No global mutable `SimulationState` object.** That would recreate the duplicated-state problem at a larger scale instead of solving it.
- **No premature plugin framework** for future domains (inventory, procurement, finance, workforce, maintenance). The P2 state-query-interface pattern is scoped narrowly and should be validated against one real new domain before generalizing further.
- **No rewriting all handlers at once.** The backlog is staged specifically so `IntegratedHandler`, `FactoryHandler`, and `DemandModel` can be changed independently and reviewed in small, testable increments.
- **No fixing the Rust-era documentation staleness** (`CONTRIBUTING.md`'s crate/Cargo references, `docs/standards-alignment.md`'s "Crate" column) as part of this pass — real, but orthogonal to the Events–State–Observations philosophy this task scopes. Worth its own follow-up.
- **No implementation of the P0/P1/P2/P3 backlog items themselves** in this pass, beyond the documentation changes listed in section A — per the task's instruction to produce a staged backlog rather than execute the refactor. (The one exception remains the already-merged `SnapshotBuilder` fix from the original pass, whose semantics this update partially amends without re-touching the code.)
- **No sophisticated accounting model** (refined 2026-08-20 (2), was "no accounting/finance model"). A minimal Finance domain with a minimal double-entry ledger *is* the intentional current architecture, not a non-goal — see the "Finance established as a domain, now" update above. What remains explicitly out of scope: GAAP/IFRS compliance, configurable revenue-recognition frameworks, `AccountsReceivable`/`AccountsPayable` unless an actual scenario needs them, payment terms, tax, depreciation, multi-currency, debt/equity financing, inventory accounting, budgeting, forecasting, fiscal periods/closing, a generalized accounting rules engine, or ERP abstractions. `CompletedSalesValue` remains a Factory-owned operational/commercial KPI, distinct from (and not automatically identical to) whatever Finance eventually calls its Sales balance.
- **No generic event bus merely to accommodate Finance.** `OrderCompleted` is one more explicit event type dispatched through the same `Scheduler`/`IntegratedHandler` sequencing as everything else — Finance does not justify async dispatch or pub-sub any more than any other domain did.

## E. Suggested target architecture

```text
             Events
                |
                v
        Domain-owned State
                |
                v
     Read-only Observations
                |
                v
     Agents / Policies / Experiments
                |
                v
        Decisions / Commands
                |
                v
              Events
```

Concretely, for Arcogine as it exists today plus its near-term direction:

- `PricingState`, `FactoryHandler`, and future `InventoryHandler`/`FinanceHandler`/`WorkforceHandler` each own one slice of mutable state, mutated only inside their own `handleEvent`, with no cross-domain setters between them. `PricingState` owns `OfferPrice`; `FactoryHandler` owns each order's immutable `OrderPrice`/`OrderValue` (arriving on `OrderCreation`, never queried back from `PricingState`) and the derived `CompletedSalesValue`.
- Historical transaction facts travel *with the event that created them*, not through a later query against current state — `OrderCreation` carries the agreed `unitPrice`, so `FactoryHandler` never needs to ask "what's the price" after the fact; it already knows, from the event, what price applies to that specific order for its entire lifecycle. This is the concrete illustration of why event payloads should carry the facts a downstream domain needs, rather than requiring that domain to read another domain's live mutable state later.
- Cross-domain reads happen through narrow, read-only interfaces (the P2 state-query-interface pattern) or through purpose-specific `XObservation` records — never through a shared mutable field or a direct setter call from `IntegratedHandler`.
- `IntegratedHandler` stays the explicit, deterministic composition root — its job shrinks to *sequencing* handler calls in a documented order, not *synchronizing* their internals or *assembling* observations. Observation construction moves to small projector functions colocated with the observation type they build (following `AgentObservation`'s example).
- Agents and any future policy/experiment code only ever see Observations, and only ever produce Events/Decisions — `SalesAgent.decide()` is already the model to replicate. An agent can change `OfferPrice` for the future; it can never reach an existing order's `OrderPrice`.
- API/UI snapshots (`SnapshotBuilder`) remain a legitimate, separate projection for external consumers, but are documented as such and are never a second authority for a number (like `CompletedSalesValue`) that a domain observation also reports — the two must be demonstrably consistent, enforced by tests.
- Adding a new domain means: (1) a new `XHandler` implementing `EventHandler` that owns its own state, (2) a new `XObservation` record for whatever needs to read it, (3) one line in `IntegratedHandler`'s explicit sequence — not new setters scattered across existing handlers.
- Finance is the first concrete application of that pattern: `OrderCompleted` (an `EventPayload`, the operational fact) → `FinanceHandler` (owns `Ledger`, posts balanced `JournalEntry` records) → a `FinanceObservation` (read-only, purpose-specific) for whatever eventually needs to see cash/sales/receivables. Commercial truth (`OrderPrice`/`OrderValue`, fixed at `OrderCreation`), operational truth (`OrderCompleted`, fixed at fulfillment), and financial truth (the `JournalEntry` Finance derives from it) stay three distinct, separately-owned facts connected only by events — never by one domain reaching into another's state.

This preserves everything the constraints require — deterministic behavior, explicit ordering, module boundaries, headless-first design, testability, replayability — while removing the specific couplings this assessment found in `IntegratedHandler`, `DemandModel`, and `FactoryHandler`.
