# Events–State–Observations Architecture Assessment

> **Date:** 2026-08-20
> **Scope:** Formalize the Events–State–Observations philosophy as a first-class architectural principle, assess the current Java implementation against it, and produce a staged backlog. This document does not implement the refactor.

## Canonical invariant

```text
Events mutate State.
State produces Observations.
Observations inform Decisions.
Decisions produce Events.
```

See `docs/architecture.md` (section "Core Architecture Philosophy: Events, State, Observations") for the full narrative treatment of Events, State, Observations, and Decisions, and for the list of signals that should trigger architectural review.

## B. Current-state architecture matrix

| Area | Status | Evidence | Risk | Recommended action |
|---|---|---|---|---|
| `Event` / `EventPayload` (sim-core) | **Aligned** | Both are Java records; `EventPayload` is a `sealed interface` with 8 record permits; `Event.of()` derives `EventType` via exhaustive pattern match. Fully immutable, inspectable, replayable via `EventLog`. | Low | None. Use as the template for future event types. |
| `EventHandler` contract (sim-core) | **Aligned** | Single-method functional interface; all domain handlers (`PricingState`, `DemandModel`, `FactoryHandler`, `SalesAgent`, `IntegratedHandler`) implement it uniformly and only mutate their own state in response to events. | Low | None. |
| `Scheduler` same-tick ordering (sim-core) | **Needs design decision** | `PriorityQueue<Event>` ordered only by `Comparator.comparing(Event::time)` — no tie-breaker for equal-`SimTime` events. `FactoryHandler.tryDispatchFromQueue` schedules `TaskStart`/`TaskEnd` at the same tick in some paths, so same-tick collisions are real, not hypothetical. | Medium — silently non-deterministic ordering among equal-time events would violate the documented determinism contract. | Decide and document an explicit tie-break rule (e.g. FIFO by insertion sequence number, or an explicit priority per `EventType`), then add a determinism test asserting stable same-tick ordering across runs. |
| `PricingState` (sim-economy) | **Misaligned** (as sole owner) | Owns `currentPrice` + `priceHistory`, mutated only via its own `handleEvent`/`setPrice` — good ownership in isolation. But `DemandModel` and `FactoryHandler` each keep a **separate mutable copy** of "current price," so `PricingState` is not the exclusive representation the philosophy calls for. | Medium — three copies of the same fact, kept in sync only by `IntegratedHandler`'s per-event push order. | See P0/P1 backlog items on removing duplicate price fields. |
| `DemandModel` (sim-economy) | **Transitional** | `currentPrice`/`avgLeadTime` are mutable fields pushed in unconditionally by `IntegratedHandler` on *every* event (`IntegratedHandler.java:38-39`) **and** independently updated by `DemandModel`'s own `PriceChange` case (`DemandModel.java:79`) — two update paths for the same field. `generateOrders()` also schedules `OrderCreation` events directly, mixing "state" and "decision" responsibilities in one class. | Medium — redundant-but-currently-consistent sync paths are exactly the kind of thing that silently diverges under a future edit. | Pick one update path (event-driven only); stop the unconditional per-event push from `IntegratedHandler`. |
| `FactoryHandler` (sim-factory) | **Transitional / Misaligned** on price | Owns machines/jobs/queues/routing (good — single owner, mutated only via its own `handleEvent`). But also holds a `private double currentPrice` field that is a copy of `PricingState.currentPrice`, defaulting to `0.0` until the first event flows through `IntegratedHandler` (`HandlerFactory` never initializes it). `totalRevenue`/`completedSales` are **public mutable fields**, not encapsulated. | Medium — the `0.0` initial price is a latent bug window (any revenue-affecting event processed before the very first `IntegratedHandler.handleEvent` call would use the wrong price); public mutable fields let any caller in `sim-api` write to factory-owned state directly. | Encapsulate `totalRevenue`/`completedSales` behind accessors (read-only outside `FactoryHandler`); resolve price duplication per the demand-model item above; initialize (or better, eliminate) `currentPrice` at construction. |
| Revenue computation on job completion (`FactoryHandler.handleTaskEnd`) | **Needs design decision** | `totalRevenue += currentPrice * job.quantity()` at completion time — i.e., price-at-completion. `Job` never captures a price-at-order-creation snapshot. Encoded as intended behavior by `FactoryHandlerTest.revenueTrackedWithCurrentPrice`, but nowhere documented as a deliberate business rule prior to this pass. | High (semantic ambiguity, not a bug per se, but silently defines economics) | Product/domain decision needed — see Task 3 below. Until decided, treat current behavior (price-at-completion) as the documented default (now reflected in `docs/concepts.md`). |
| `SnapshotBuilder` per-job revenue (sim-api) | **Misaligned** | `JobInfo.revenue` for completed jobs is recomputed at snapshot-build time as `pricing.currentPrice() * job.quantity()` (i.e. "now"), independent of what `FactoryHandler.totalRevenue` actually accrued for that job. These two numbers can diverge for any completed job once price changes afterward. | High — concretely demonstrable, user-visible inconsistency (aggregate KPI vs. per-job breakdown disagree), and currently untested. | Treat as a near-term bug fix: `Job` (or an event payload) should carry the price actually applied at completion, and `SnapshotBuilder` should read that value instead of recomputing from live `PricingState`. |
| `IntegratedHandler` (sim-api) | **Transitional (orchestration) / Misaligned (observation construction)** | Explicit fixed ordering (Pricing → Demand → Factory → Agent) is a reasonable, deterministic composition strategy in isolation. But it also performs 3 cross-domain setter pushes every event (`demand.setPrice`, `demand.setAvgLeadTime`, `factory.setCurrentPrice`) and hand-assembles `AgentObservation` from raw fields/methods on `FactoryHandler`/`PricingState` — orchestration and observation-construction are mixed into one class. | Medium — this is the central "god orchestrator" risk called out in the task: adding a domain today means adding more pairwise pushes here. | See P1 backlog: extract observation construction to a dedicated, testable projector; keep ordering explicit but stop pushing state copies. |
| `HandlerFactory` (sim-api) | **Aligned (wiring) / carries forward the price duplication** | Cleanly constructs each handler from `ScenarioConfig` in dependency order — no issue with wiring itself. But it seeds `initialPrice` into both `DemandModel` and `PricingState` independently (two separate fields, same source value) and leaves `FactoryHandler.currentPrice` unset. | Low–Medium | Fix alongside the price-duplication items above; not a standalone risk. |
| `AgentObservation` (sim-agents) | **Aligned** | Immutable record (`backlog`, `avgLeadTime`, `totalRevenue`, `completedSales`, `currentPrice`, `throughput`), plus a `DEFAULT` singleton. Purpose-specific, matches the Observation contract structurally. | Low | None structurally; construction site (`IntegratedHandler`) is what needs to move, not the type itself. |
| `SalesAgent` (sim-agents) | **Mostly aligned** | `decide()` is a pure function over `AgentObservation` + config; on `AgentEvaluation` it *schedules* `PriceChange`/`AgentDecision` events rather than calling a setter — the cleanest Observation→Decision→Event example in the codebase. `observation` and `interventions` are public mutable fields (agent's own state, not another domain's), which is a minor encapsulation gap rather than a philosophy violation. | Low | Encapsulate `observation`/`interventions` behind accessors for hygiene; no behavioral change needed. |
| `SimThread` (sim-api) | **Mostly aligned** | All simulation mutation (`IntegratedHandler`, `Scheduler`, `EventLog`) is confined to one dedicated thread; published via `AtomicReference` safe publication (`snapshot`, `eventLog`) — correct given single-writer confinement, and good for determinism. | Low | None structurally. |
| `SimCommand.ToggleAgent` handling (sim-api, `SimThread`) | **Misaligned** | `ChangePrice`/`ChangeMachine` commands are correctly wrapped as `Event`/`EventPayload` and routed through `handler.handleEvent(...)`. `ToggleAgent` instead calls `handler.setAgentEnabled(...)` directly — a state mutation that bypasses the event system entirely, the one command handler that doesn't follow the Decision→Event pattern. | Low–Medium — currently harmless (agent-enabled is orchestration config, not domain state), but it's an inconsistent precedent for the next command that gets added. | Either model `AgentEnabled` as a proper event/state transition (if it should be replayable/loggable) or explicitly document it as configuration rather than simulation state, so the exception is deliberate, not accidental. |
| Duplicate wiring logic in tests (sim-api) | **Needs design decision / test-debt** | `AgentIntegrationTest.TestHandler` re-implements `IntegratedHandler.handleEvent`'s sync logic (price push, lead-time push, `AgentObservation` construction) locally instead of exercising the real `IntegratedHandler`. Can silently drift from production behavior. | Medium | Replace `TestHandler` with the real `IntegratedHandler` in that test, or delete the duplicate if it exists to test something `IntegratedHandler` can't. |
| Observation vs. API snapshot duality | **Needs design decision** | `AgentObservation` (agent-facing) and `SnapshotBuilder`'s DTO tree (`SimSnapshot`/`JobInfo`/`MachineInfo`, API/UI-facing) are two independently constructed, non-shared projections over the same underlying state, with no shared base or documented relationship. | Medium | Not necessarily wrong (different consumers legitimately need different shapes) — but should be a **documented** decision, not an emergent fact, especially given the revenue divergence above. |

## D. Explicit non-goals (for this pass and near-term follow-up)

- **No generic event bus / pub-sub.** Arcogine's value is explicit, deterministic, easy-to-read execution order. A bus would trade that for indirection the task explicitly asked to avoid.
- **No CQRS framework or event-sourcing framework.** The existing `Event`/`EventLog`/`Scheduler` triad already gives replayability where it's needed; adopting a framework would add ceremony without a demonstrated need.
- **No global mutable `SimulationState` object.** That would recreate the duplicated-state problem at a larger scale instead of solving it.
- **No premature plugin framework** for future domains (inventory, procurement, finance, workforce, maintenance). The P2 state-query-interface pattern is scoped narrowly and should be validated against one real new domain before generalizing further.
- **No rewriting all handlers at once.** The backlog is staged specifically so `IntegratedHandler`, `FactoryHandler`, and `DemandModel` can be changed independently and reviewed in small, testable increments.
- **No fixing the Rust-era documentation staleness** (`CONTRIBUTING.md`'s crate/Cargo references, `docs/standards-alignment.md`'s "Crate" column) as part of this pass — real, but orthogonal to the Events–State–Observations philosophy this task scopes. Worth its own follow-up.
- **No implementation of the P0/P1/P2/P3 backlog items themselves** in this pass, beyond the documentation changes listed in section A — per the task's instruction to produce a staged backlog rather than execute the refactor.

## E. Suggested target architecture

```text
             Events
                |
                v
        Domain-owned State
                |
                v
     Read-only Observations
                |
                v
     Agents / Policies / Experiments
                |
                v
        Decisions / Commands
                |
                v
              Events
```

Concretely, for Arcogine as it exists today plus its near-term direction:

- `PricingState`, `FactoryHandler`, and future `InventoryHandler`/`FinanceHandler`/`WorkforceHandler` each own one slice of mutable state, mutated only inside their own `handleEvent`, with no cross-domain setters between them.
- Cross-domain reads happen through narrow, read-only interfaces (the P2 state-query-interface pattern) or through purpose-specific `XObservation` records — never through a shared mutable field or a direct setter call from `IntegratedHandler`.
- `IntegratedHandler` stays the explicit, deterministic composition root — its job shrinks to *sequencing* handler calls in a documented order, not *synchronizing* their internals or *assembling* observations. Observation construction moves to small projector functions colocated with the observation type they build (following `AgentObservation`'s example).
- Agents and any future policy/experiment code only ever see Observations, and only ever produce Events/Decisions — `SalesAgent.decide()` is already the model to replicate.
- API/UI snapshots (`SnapshotBuilder`) remain a legitimate, separate projection for external consumers, but are documented as such and are never a second authority for a number (like revenue) that a domain observation also reports — the two must be demonstrably consistent, enforced by tests.
- Adding a new domain means: (1) a new `XHandler` implementing `EventHandler` that owns its own state, (2) a new `XObservation` record for whatever needs to read it, (3) one line in `IntegratedHandler`'s explicit sequence — not new setters scattered across existing handlers.

This preserves everything the constraints require — deterministic behavior, explicit ordering, module boundaries, headless-first design, testability, replayability — while removing the specific couplings this assessment found in `IntegratedHandler`, `DemandModel`, and `FactoryHandler`.
