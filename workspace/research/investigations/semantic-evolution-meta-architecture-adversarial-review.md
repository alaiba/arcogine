## 2. Pre-report reconstruction (anchoring control, verbatim from scratch notes)

Written before reading `c6e67cb` in depth.

**Decision actually at stake.** Whether Arcogine adopts a repository-wide rule for how semantic contracts acquire (a) non-rebinding identity and (b) continuing support obligations, and — the ground-zero variant — whether the owner's declaration that the pre-reset estate is complete and internal legitimately withdraws all pre-reset support while leaving pre-reset historical facts untouched. Secondary: which parts of PR #360/ADR-0017 are enduring principle vs mechanism vs current-contract adjudication vs planning, and whether ADR-0017 should be replaced.

**Enduring constraints already present in current authority.**
- Charter §6 causality/provenance; §7 model/version/provenance become fundamental; §9 current API/modules are not identity. The Charter says nothing about compatibility promises or support windows — those are architecture.
- A pattern repeated across Accepted ADRs: identity/non-rebinding is immediate at acceptance/publication (ADR-0008 acceptance boundary; ADR-0013 §5/§10; ADR-0016 §3); corrections are new records; retention/decoding/execution are separately scoped (ADR-0015 §14/§16; ADR-0016 §3 "no perpetual byte retention", §9 bounded retention with truthful gap; ADR-0013 §4 declared bounded retention is not a break); external representation is a projection and becomes supported only when the owning capability declares an information set (ADR-0012 §14).
- Eager outliers: ADR-0014 §8 (permanent decoder retention for every released Factory policy), §9 (V1 "fully supported"); ADR-0006 "released policies immutable" (an identity rule, survives) and a bounded "compatibility period" for `contentHash`.
- Pre-release amendability already exists on `main` (Factory v2 §10; Engine v1 status/§14; Engine v1 §1.1.3), in tension with `engine-evolution.md` L11.
- Planning already holds V2 release / permanent coexistence; `governance-continuity.md` says the file adapter is proving, not production persistence.

**Identity vs support — where the separation is NOT clean.**
- A policy-defined referent (fingerprint under policy P, semantics version S) is meaningful only relative to its definition. Non-rebinding therefore entails a minimum retained basis: the exact definition revision must stay resolvable (ADR-0015 §14, ADR-0016 §9). Identity without definition retention is an opaque number.
- Content retention is separable from identity, but a digest with missing content proves neither readability nor meaning (ADR-0016 §9); bounded retention must disclose the gap.
- Operational continuation (ADR-0013): the ability to answer for accepted facts is constitutive of identity; undeclared loss = fork. "Support can be bounded" must be phrased "bounded only by declared, recorded bounds; undeclared loss is falsification/fork", or the principle is too weak for Operational.

**Candidate models.** M1 eager durability (closest to ADR-0014 §8/§9). M2 identity immediate; support explicit per dimension; optional lifecycle mechanism. M3 product-continuity primary; derive per-contract rules. M4 class-specific only. **M5a Epoch/reset-boundary:** an epoch is (i) an estate-wide support withdrawal act, (ii) an authority rule for who may declare it, (iii) a non-confusion rule across the boundary. (i) is M2's explicit scoping applied to "all pre-reset contracts, scope = none"; (iii) is already implied by non-rebinding plus label non-reuse (ADR-0006, ADR-0015 §12) — a label may persist only if meaning is unchanged. What is genuinely additional is (ii) and the requirement that the boundary itself be a recorded declaration (ADR-0013 "declared loss" analogue). Expected result: the epoch model reduces to M2 plus a recorded reset declaration; not a distinct architecture, but the declaration rule is a real qualification. **M5b Promise-scoped states** (per contract × promise) — a refinement of M2, strictly finer than contract-level proving/promoted; matches ADR-0012 §14's shape. **M5c Declaration-only, no states:** each owning contract states what it supports; silence = no support beyond non-rebinding identity plus definition retention. Simplest no-new-abstraction candidate; = M4 plus one shared minimum.

**Adversarial cases prepared.** (1) Definition amended in place pre-ship while an artifact already computed under the old definition exists → silent label rebinding; Factory has structural protection (policy-domain prefix plus fingerprint verification on artifact resolution), Engine has none. (2) Test fixtures/golden vectors as "custody": tests are proving artifacts; golden vectors are contract content. (3) Accidental external constituency: ADR-0012 §14 already says the existence of an artifact is not a support contract. (4) Internal consequential use: `ChangeSetFactory` + file authority; no production store. (5) "Accepted use" precision: acceptance = an authority's commit boundary; tests, temp dirs, drained events, local runs are not accepted uses; a store that has not declared custody is not an authority; later-discovered pre-reset custody contradicts the declaration → recorded discovery, not silent adoption. (6) Section-level Engine freeze: ADR-0015 §1/§5 make the identity the definition (complete interpretation), not the outcome function on the exercised domain; rejection outcomes are results; retained-run input-domain classification is a hidden custody assumption; reset makes section freeze unnecessary if pre-release amend-in-place is the rule and post-release = new version. (7) Grandfathering V1 not logically required; separate (a) withdrawable compat, (b) invariants to keep (policy = canonicalization contract; label change on identity-affecting change; prefix discrimination; no auto-lift; explicit cross-policy comparison; revision ≠ fingerprint; Unicode totality), (c) deletable implementation, (d) domain decisions the meta-report must not settle. (8) Charter: no change expected; Charter provenance constrains the reset (withdraw support, never rewrite facts). (9) Authority placement: principle → Overview prose (attribution-section precedent); reset decision + withdrawal of ADR-0014 §8/§9 → superseding ADR; ADR-0006/0015 probably not superseded; the Engine pre-release tension must be resolved somewhere. (10) No-new-research: reset legitimacy is an owner declaration, not research; section freeze needs research only if kept; composition/analytics/Operational closure stay separate.

## 4. Challenges, evidence, and results

Format: challenged → evidence → result → effect. Labels: Repository fact / External evidence / Inference / Qualification.

### A. Ground-zero authority and sufficiency

- **Challenged:** whether an owner declaration legitimately withdraws the pre-reset support estate; whether obligations survive absent any external constituency; whether the report separates support withdrawal from rewriting history; whether a reset boundary suffices without a stronger epoch/namespace rule.
- **Evidence:** Repository fact — Charter §10/§12 make the Charter the product authority and ADRs supersedable, never silently overridable; ADR README requires supersession when a decision's applicability changes; ADR-0014 §8/§9 are the only Accepted promises of permanent Factory decoder retention/"full support"; ADR-0012 §14 already states that the existence of an artifact/serializer is not a supported contract; the repository has no releases/tags/publishing workflow and no outward exposure of any semantic identity (§1). Report — grounds the reset in the owner's declaration "rather than an absence inference", requires "a new Accepted reconciliation" superseding conflicting decisions, keeps Git/ADR history, and says the reset "is not a license to reuse an identifier … for changed meaning".
- **Result:** Survives. Withdrawal of support recorded in Accepted ADRs is legitimate only through supersession, and the report says so. No obligation to a pre-reset consumer survives because the only source of such an obligation on `main` is accepted use or a published promise, and the owner declares none exists; git history plus immutable ADR text satisfy Charter provenance for the pre-reset estate. Support withdrawal and history rewriting are cleanly separated. The **epoch model reduces** to the report's proposal: an estate-wide withdrawal (principle 4's "explicit authorized transition"), a recorded boundary (the reset ADR), and identifier non-reuse. It is not an omitted viable model. Two sharpenings are needed (Q1, Q2): the declaration itself must be recorded as dated context in the reset ADR so the reset's legitimacy is inspectable without conversation history, and identifier non-reuse across the boundary must be a rule, not advice — with the Factory/Engine asymmetry made explicit. On `main`, a pre-reset Factory artifact cannot be confused with a post-reset one unless the same policy-domain prefix is reused for different bytes (fingerprint verification then fails loudly); Engine has no structural discriminator, and although no observation/event on `main` carries the Engine label, `FactoryRuntime.semanticsVersion()` already exposes `engine-semantics:v1`, so a hand-recorded pre-reset attribution is possible in principle. Keeping any pre-reset label post-reset is safe only when its definition is unchanged rule-for-rule.
- **Effect:** conclusion holds; Q1, Q2.

### B. Scope of the four proposed principles

- **Challenged:** whether they are enduring or current mechanism generalised upward; too broad for accumulating identities; too narrow for audit/provenance; whether any belongs in the Charter.
- **Evidence:** Repository fact — principle 1 restates ADR-0008 (immutable core, corrections explicit), ADR-0013 §10, ADR-0016 §3; principle 3 restates ADR-0015 §14/§16, ADR-0016 §9, ADR-0013 §4; the Overview already carries research-derived cross-domain rules as prose (attribution section). External evidence — PROV-DM's fixed-aspects entity supports principle 1's "declare what changes and what remains fixed" for accumulating identities. Charter §6–§7 supply the purpose (provenance, consequence-scaled control).
- **Result:** Survives with one placement qualification. Principles 1–3 are the convergent content of five Accepted decisions in three domains, not a generalisation of PR #360's mechanism. The accumulating-identity clause plus the report's "separable but not independent" section handle Operational correctly (ADR-0013 §4 continuity is stronger than an optional support promise, and the report says continuity rules "still apply"). Nothing requires a Charter amendment; principle 2 is derivable from Charter §7 ("accepted actions… cannot be collapsed") and "Safety scales with consequence". Principle 4 mixes an invariant ("preserve original accepted bindings… narrowing an in-scope promise requires an explicit authorized transition") with a checklist ("state the successor's meaning, supported scope, compatibility evidence and retirement effects"); only the invariant half is enduring architecture.
- **Effect:** conclusion holds; Q3.

### C. "Accountability follows accepted use"

- **Challenged:** whether "accepted use" is a precise obligation trigger; who accepts and where that authority is represented; whether it creates hidden obligations less reviewable than ADR-0017 §3's two enumerated sources; handling of accidental, implicit, internal, and later-discovered use.
- **Evidence:** Repository fact — ADR-0008, ADR-0013 §5, ADR-0016 §8 all locate acceptance at an authority's commit boundary; ADR-0013 §5.3 excludes received/provisional/rejected material from the accepted set; the prior review's Q2 already found that "accepted at a commit boundary" alone cannot separate a test authority from a retained one. Report — case 6 "missing support metadata is an admission defect, not a waiver"; mechanism section "silence is not evidence of a support claim… an undeclared retained-use horizon should block new admission"; §3 row "obligations follow accepted use and published authority"; falsification trigger for a later-discovered client.
- **Result:** Survives, but the trigger is under-specified in the report's own text. The report's position is coherent: obligations arise from a published declaration or from acceptance into declared retained custody; accepting without a custody declaration is a defect that must be accounted for, not a waiver. That is at least as reviewable as ADR-0017 §3 **provided the reconciliation states it enumerably**: "accepted use" means acceptance by an authority that has declared its custody, at that authority's commit boundary, or reliance published by the owning contract; tests, scratch stores, drained events, and local runs are not accepted uses; acceptance by an undeclared store is a defect resolved by accounting, never by retroactive disposal. Accidental third-party reliance (public repository) is correctly excluded — ADR-0012 §14 already establishes that artifact existence is not a promise. Later-discovered use is correctly handled by the falsification trigger.
- **Effect:** conclusion holds; Q4.

### D. Identity versus support dimensions

- **Challenged:** whether historical meaning/non-rebinding can remain separate from retention/decoding/execution while satisfying audit; whether some identities entail a minimum retained basis; whether bounded support can expire without making meaning unverifiable; whether a digest is equated with an explanation.
- **Evidence:** Repository fact — ADR-0015 §14 ("attribution plus a verifiable definition"); ADR-0016 §9 ("a retained digest with missing content proves neither readability nor meaning"); ADR-0013 §4 (declared bounded retention is not a break; silent loss is a fork). Report — "separable, but not independent"; "a permanent decoder promise implies maintaining some executable decoding capability"; principle 3's digest clause; "a horizon is not permission to delete another accepted use's basis".
- **Result:** Survives. The report does not equate digest with explanation and correctly identifies that a supported explanation carries a real retention dependency. One floor is implicit but unstated: attribution of an accepted record to a definition identity is itself a claim of historical explanation of that record's interpretation, so **definition retention follows for every identity Arcogine stamps on an accepted or retained record**, independently of any further declared promise. ADR-0015 §14 and ADR-0016 §9 already require this; the report leaves it to per-contract declaration, which is marginally weaker than current authority.
- **Effect:** conclusion holds; Q5.

### E. Rejection of a universal proving/promoted lifecycle

- **Challenged:** whether the report shows the two-state mechanism unnecessary or only mis-united; whether promise-scoped states solve the objections more cleanly; whether removing the global mechanism weakens an admission/refusal invariant; whether a universal lifecycle creates false precision.
- **Evidence:** Repository fact — Factory v2 §10 and Engine v1 §14 already carry implicit pre-release states with different triggers; a whole-contract binary would be a third vocabulary; `FileControlledRevisionAuthority` already refuses artifacts with no registered verifier (the executable refusal invariant). Candidate text — ADR-0017 §3 exclusivity; §9/Overview describing Engine as promoted attribution plus proving execution (verified). Report — concedes proving/promoted "may be useful descriptions of a specified promise and scope"; keeps "prevention of unresolvable retained acceptance" and "silence is not evidence of a support claim".
- **Result:** Survives as the narrower claim the report actually makes: the whole-contract exclusive state is the wrong unit and not enduring architecture; per-promise declarations are the coherent form (the same shape ADR-0012 §14 already uses). No admission/refusal invariant is lost: the verifier-registration refusal, exact-revision-plus-custody recording on retained acceptance, and "silence is no support" are all retained. What is lost relative to ADR-0017 §3 is *enumerability*; Q4 restores it without reintroducing the state machine.
- **Effect:** conclusion holds; no additional qualification beyond Q4.

### F. Support declaration mechanism

- **Challenged:** sufficiency and enforceability of an owning-contract declaration; minimality of its information set; silence/new admission without a registry; obligation versus evidence of fulfilment.
- **Evidence:** Repository fact — ADR-0012 §14's information set (identity/version, semantic source, provenance fields, meaning/units, ordering, evolution policy, validation, fixtures); ADR-0017 §6's seven-item record. Report — exact revision, supported scope, obligation source, preserved basis/custody, decoding/execution/interface guarantees, evidence and limitations, change/retirement behaviour; "a support declaration is not proof that the implementation already fulfils it".
- **Result:** Survives. The information set is the union of what current authority already asks for at the outward boundary and the retention/definition items the identity rules require; nothing load-bearing is missing (failure behaviour is named in the post-reset estate section and case 6; it should appear in the list itself at reconciliation). Enforceability is domain-executable (verifier registration; custody declaration at admission). No registry is needed. Obligation and fulfilment are kept distinct.
- **Effect:** conclusion holds; minor drafting note folded into Q4.

### G. Engine same-identity amendment / section freeze

- **Challenged:** the report's rejection of universal exercised-section freezing; whether section-level or supported-input-domain evidence could justify a same-identity correction; whether the candidate rule can silently rebind `engine-semantics:v1`; whether bounded Engine research is required before any same-label amendment.
- **Evidence:** Repository fact — ADR-0015 §1 and §5 define the version as the identity of the **complete** interpretation with an enumerated normative specification; §4 rejects sub-policies because rules interact; §12 makes released versions immutable "including a bug fix"; Engine v1 §1.1.1 counts rejection bounds as semantic rules; Engine identity is not propagated to observations/events. Candidate text — Engine v1 §15.1 names "this document" as the exact definition revision; §15.3 declares the exercised set to be "everything reachable without spatial facts". Prior review Q4 introduced the section rule as a sharpening, not as a proved necessity.
- **Result:** Survives. Under ADR-0015 the identity denotes the definition, so a same-label change to any rule's behaviour rebinds the identity regardless of whether a retained run's outcome differs; a mutable "this document" is not an exact revision; the reachability claim in §15.3 is itself an evidence obligation. The report's rejection is correct and its concession (a bounded investigation could establish a narrower identity boundary) is appropriately open. The report **misses the simpler rule current authority already contains**: Factory v2 §10 freezes the *whole definition* at first shipped fingerprint or first acceptance into retained custody. Generalised — a pre-release normative definition may be amended in place only until the first accepted/retained record is attributed to it, after which any behavioural change is a new identity — this needs no section granularity, no reachability analysis, and no research, and it resolves the `engine-evolution.md` L11 tension in favour of "no exception once attributed, amendable before". Because Engine identity is exposed by `FactoryRuntime` today, the post-reset Engine contract must either not stamp its identity on retained/accepted records before freeze or declare such records disposable.
- **Effect:** conclusion holds; the report's research gate 1 remains correct **only** for post-attribution same-label amendment; Q6 adds the whole-definition trigger.

## 6. Disposition

**ACCEPT WITH QUALIFICATIONS.**

**What survived.** The load-bearing conclusions all survived: (1) an explicit, owner-directed, ADR-recorded reset legitimately withdraws the pre-reset support estate without rewriting history; (2) identity/non-rebinding and continuing support are distinct but not independent, and a digest is not an explanation; (3) a whole-contract, mutually exclusive proving/promoted state is the wrong unit and not enduring architecture — per-promise declarations in the owning contract suffice; (4) universal exercised-section freeze must not be ratified; (5) the four principles are enduring, Charter-derived architecture requiring no Charter amendment; (6) no new bounded research is needed to ratify the reset boundary and the minimal principles; (7) authority placement matches the hierarchy; (8) the epoch/reset-boundary model reduces to the report's proposal and is not an omitted candidate.

**What failed or was found stronger than its evidence.** No headline conclusion was falsified. The current-contract table over-reaches in three rows (Factory V1, Governance, Operational) by treating a support reset as licence to reopen Accepted semantic decisions (ADR-0003/0004/0006 identity concept; ADR-0008/0016 invariants; ADR-0013 continuation rules) with no evidence — the Operational row directly contradicts the report's own case 8 and research gate 3. The report also omits three rules current authority already supplies (label non-reuse as a rule; the whole-definition freeze trigger; the definition-retention floor), leaves "accepted use" less enumerable than the mechanism it replaces, and omits ADR-0006 from the supersession inventory.

**Effect on the recommendation.** Unchanged in direction: keep PR #360 unmerged, replace its monolithic proposal with a layered ground-zero reconciliation. The reconciliation must carry the qualifications below; with them, the report is decision-quality evidence for that reconciliation.

## 7. Qualifications that must survive durable reconciliation

Each names its owning durable surface so reconciliation can map it.

- **Q1 — Record the reset's ground.** The reset ADR's Context must record the owner's complete-estate declaration as a dated statement (scope: no client, retained artifact, external store, release, deployment, or external consumer), so the reset's legitimacy is inspectable from repository content alone. The declaration is an owner fact, not an absence inference; the ADR must say so and must keep the report's falsification trigger (an excluded use surfaces → stop, inventory, decide). *Owner: reset ADR.*
- **Q2 — Identifier non-reuse across the boundary is a rule.** A post-reset identity may bear a pre-reset label only if its definition is unchanged rule-for-rule/byte-for-byte; otherwise a fresh label or namespace is mandatory. State the asymmetry: Factory identities are structurally discriminated by policy-domain prefix plus verification; Engine identities are not, so a post-reset Engine identity must not reuse `engine-semantics:v1` unless the definition is identical. *Owner: reset ADR (rule); Overview (compact statement); Engine/Factory specs (application).*
- **Q3 — Keep only the invariant half of principle 4 in the Overview.** "Preserve original accepted bindings and domain ownership; narrowing an in-scope promise requires an explicit authorized transition" is enduring. "State the successor's meaning, supported scope, compatibility evidence and retirement effects" is the support-declaration checklist and belongs with the mechanism (development policy / owning specs). *Owner: Overview vs development policy.*
- **Q4 — Make "accepted use" enumerable.** An obligation arises only from (a) reliance published by the owning contract's support declaration, or (b) acceptance by an authority that has declared its custody, at that authority's commit boundary. Tests, scratch stores, drained events, and local runs are not accepted uses. Acceptance by an undeclared store is an admission defect: obligations are accounted for, never retroactively disposed, and new admission is blocked until custody is declared. Include failure behaviour in the declaration's information set. *Owner: reset ADR (rule) + development policy (declaration content) + Governance architecture (executable form).*
- **Q5 — Definition-retention floor.** Every identity Arcogine stamps on an accepted or retained record entails retention of that identity's exact definition revision for as long as the record is retained; content retention, decoding, execution, and interoperability remain separately declared. This restates ADR-0015 §14 and ADR-0016 §9 cross-domain. *Owner: Overview principle 3 wording.*
- **Q6 — Whole-definition freeze trigger for pre-release normative contracts.** A normative-specification contract may be amended in place only until the first accepted/retained record is attributed to it (Factory v2 §10's existing trigger, generalised); thereafter any behavioural change is a new identity. Drop section granularity. Resolve `engine-evolution.md` L11 to this rule. The post-reset Engine contract must not stamp its identity on retained/accepted records before freeze, or must declare such records disposable. Bounded Engine research remains required only for post-attribution same-label amendment. *Owner: reset ADR or Engine/Factory specs; `engine-evolution.md` propagation.*
- **Q7 — Confine the reset to support withdrawal; classify every row explicitly.** For each of Factory V1, Factory V2, Engine V1, Governance history/evidence, runtime/outward, Operational, and legacy hash, the reconciliation must list (a) withdrawn obligations, (b) retained-intrinsic invariants, (c) deletable implementation, (d) unresolved domain decisions. In particular: retain ADR-0006's policy-level invariants (policy version = canonicalization contract; identity-affecting change ⇒ new label; digest independent of serializer; totality over published models), ADR-0004/0008's fingerprint ≠ revision rule, ADR-0014 §4/ADR-0015 §3's authored-fact vs Engine-interpretation ownership, ADR-0014 §10–§12's no-lift/explicit-comparison invariants, ADR-0011/0012's derivation and projection rules, and **ADR-0008, ADR-0013, ADR-0016 in full** — nothing in this report or the reset supplies evidence to reopen them, and the Operational row's "re-evaluate ADR-0013" must be removed (there is no Operational support estate to withdraw). Any broader re-decision of those semantics is a separate, evidence-bearing decision outside the reset. *Owner: reset ADR classification table; Operational/Governance architecture untouched.*
- **Q8 — No duplicated authority.** The Overview's compact doctrine cites the owning ADRs for each invariant and does not restate their decisions; the reset ADR records the reset, the withdrawals, and the supersessions, and does not restate the Overview. *Owner: Overview + reset ADR.*
- **Q9 — Supersession inventory includes ADR-0006.** If `factory-model:v1` ceases to be a supported policy, ADR-0006's applicability changes (its golden-vector and cross-implementation obligations bind "every supported implementation"); either supersede it with an explicit carry-forward of its policy-level invariants or record, in the reset ADR, that v1 remains a supported policy. ADR-0014 is superseded with its §4 and §10–§12 invariants carried forward. ADR-0011, ADR-0012, ADR-0015 need no supersession. *Owner: reset ADR metadata.*
